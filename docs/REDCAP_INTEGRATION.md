გაურკვეველი გაუქმება სტატუსის კითხვით მოწმდება. გაუქმებული გზავნილის ხელახლა
დაჯავშნის ავტომატური ფუნქცია ამ ეტაპზე არ არის.

**RedCap სინქრონიზაციის ანგარიშები:** ცვლილებები და პრობლემები. უცვლელი წარმატებული
შემოწმება ახალ ანგარიშს არ ქმნის; ბიზნეს პანელი ბოლო შენახულ ანგარიშს აჩვენებს,
ხოლო თითო გზავნილს საკუთარი შემოწმების დრო აქვს. სტატუსები არ იწყებს refund-ს,
მარაგის აღდგენას და არ ხსნის გაუქმებულ/დაბრუნების პროცესში მყოფ შეკვეთას.

## გაუქმება და თანხის დაბრუნება

ავტორიზებული დოკუმენტაცია ხელახლა წაკითხულია:
https://redcap.ge/dashboard/api-docs — `/orders/{tracking}/cancel` და `/return`.
დოკუმენტაციით `/cancel` მიიღება მხოლოდ `registered` („გაფორმებული“) სტატუსზე;
კურიერის დანიშვნა უკვე კეტავს გაუქმებას, თუნდაც ამანათი ჯერ გამგზავნთან იყოს.
მოთხოვნაა POST მიზეზით; უარის კოდია 403 `CANCEL_NOT_ALLOWED`.
`/return` ქმნის ახალ გზავნილს გამგზავნისა და მიმღების ადგილების შეცვლით;
იგი არც საწყისი გზავნილის გაუქმება და არც საბანკო refund არ არის.
უკუგზავნილის ავტომატური შეკვეთა ამ ეტაპზე არ არის ჩართული. ამ შემოწმებისას
მხოლოდ დოკუმენტაცია გაიხსნა; რეალური cancel/return/refund არ გაგზავნილა.

ოპერატორის გზა:

1. ჯერ არშექმნილი ან აშკარად უარყოფილი გზავნილი გაუქმებას არ საჭიროებს.
2. შექმნილი გზავნილისთვის: „RedCap გზავნილის გაუქმება“ → მიზეზი → პროვაიდერის
   წარმატებული პასუხი → არსებული ბანკის თანხის დაბრუნების ფორმა და ნივთების
   მდგომარეობის დადასტურება. შეკვეთის გაუქმება/მარაგის საბოლოო დამუშავება ხდება
   ბანკის დადასტურებით; კურიერის cancel ამას თავისით არ აკეთებს.
3. თუ კურიერი დანიშნულია ან ამანათი უკვე გადაცემულია, RedCap-თან უნდა შეთანხმდეს
   შეჩერება/ფიზიკური დაბრუნება. გაგზავნილი ნივთის საბანკო refund-ს ჩვენთან ჯერ
   მიღება და შემოწმება სჭირდება. მათი დაბრუნების საფასური/შეჩერების პირობები
   ამ მოკლე API დოკუმენტაციაში დადასტურებული არ არის.

დამატებული დაცვა: აქტიური, შექმნის ან გაუქმების გაურკვეველი შედეგის მქონე
RedCap გზავნილი ბლოკავს გაგზავნამდე refund-ს. ეს მოწმდება backend სერვისშიც,
მანამ, სანამ საბანკო მოთხოვნა ან ნივთების მარაგში მიღება მოხდება; ძველი გახსნილი
ფორმის POST-იც ვერ აუვლის. სტატუსი მხოლოდ `cancelled` დადასტურების შემდეგ ითვლება
გაუქმებულად. მომხმარებლისგან რეალურად მიღებული `from_customer` დაბრუნება ცალკე
გზაა და თავდაპირველი გზავნილის API cancel-ს არ ითხოვს.
RedCap-ის პანელიდან შესრულებული გაუქმებაც სტატუსის შემოწმებით ინახება,
მაგრამ თანხისა და FlexDrive შეკვეთის მდგომარეობა ოპერატორის მოქმედებამდე უცვლელია.
გაუქმების POST-ისა და სტატუსის შემოწმებას შორის შეცვლილ მდგომარეობაზე საბოლოო
გადაწყვეტილებას პროვაიდერი იღებს; უარყოფილი მოთხოვნა refund-ს არ ხსნის.
ამ ცვლილებას ახალი მიგრაცია არ სჭირდება.

## ბუღალტერიის პანელი და Excel

RedCap-ის თბილისის და რეგიონების თანხა ერთნაირად საკურიერო მიწოდებაა.
შეკვეთის ბლოკში ჩანს „RedCap-ის მიტანა“, ხოლო საერთო ჯამებსა და Excel-ში —
„საკურიერო მიტანა“. თანხა მოდის შეკვეთაზე გაყინული `carrier_delivery_cost`-დან,
თითო გადახდის/დაბრუნების მოვლენაზე ერთხელ; პროდუქტის თითო ხაზზე არ მრავლდება
და ანგარიშის გახსნისას დღევანდელი ტარიფით არ გადაითვლება.
ბუფერი კვლავ შენახული `delivery_margin`-ია; ახალ RedCap შეკვეთებში ის ნულია.
სრული refund-ის გაერთიანებულ ანგარიშში თანხა ერთხელ გამოაკლდება.
პროდუქტის ძიებისას საკურიერო ხარჯი ერთ პროდუქტს არ მიეწერება.

ძველი შიდა მიტანის ცალკე სვეტი მხოლოდ ისტორიული წაკითხვისთვის დარჩა და
დასათაურებულია „შიდა მიტანა (ძველი)“. ახალი RedCap შეკვეთის ბლოკში
დამატებითი თბილისის საფასური აღარ ჩანს. ისტორიული EasyWay თანხებიც იკითხება;
არც შეკვეთები და არც ბუღალტრის უფლებები ამ UI შესწორებით არ იცვლება.

## მომხმარებლისთვის სტატუსის ჩვენება

RedCap-ის შემოწმება აახლებს არსებულ `Order.status`-ს. ამავე ველს კითხულობს
პირადი კაბინეტის შეკვეთების სია/დეტალი, სტუმრის lookup და წარმატებული შეძენის
token-გვერდი. ამიტომ კურიერის `picked_up` → ჩვენი `shipped` → UI-ის „გზაშია“
ყველა ამ გზას ერთნაირად სწვდება. პირად დეტალში არსებული ეტაპების ზოლია;
სტუმრის ფორმა შეკვეთის ნომერსა და შესაბამის ტელეფონს ითხოვს, reCAPTCHA-ით.
პირადი კაბინეტის API მხოლოდ ანგარიშის საკუთარ შეკვეთებს აბრუნებს.

ამჟამად საჯარო პასუხებში RedCap-ის დეტალური ისტორია, თრექინგის ნომერი და
შიდა შეცდომები არ იგზავნება; მომხმარებელი ხედავს საერთო შეკვეთის სტატუსს.
დეტალური საკურიერო ინფორმაცია ადმინშია. frontend არ უკავშირდება კურიერს.
გვერდები არ არის live push/polling: პირად კაბინეტში მონაცემები ხელახალი
ჩატვირთვისას იკითხება; სტუმრის ფორმაში ახალი პასუხი შემოწმების ხელახალი
დადასტურებით მოდის. სტუმრის გვერდზე დამატებულია „სტატუსის განახლება“ და
ბოლო წარმატებული შემოწმების დრო (თბილისის დროით). ხელახლა გახსნისას session-ის
შედეგი მკაფიოდ მონიშნულია როგორც წინა შემოწმების შენახული შედეგი; ეს თავისთავად
ახალი მოთხოვნა არ არის. ძველი ჩანაწერისთვის დრო არ გამოიგონება, ხოლო
წარუმატებელი მოთხოვნა ძველ სტატუსს ახალი დროით არ აჩვენებს. შენახვის შეუძლებლობა
წარმატებულ პასუხს არ ბლოკავს. შეკვეთის ნომრის/ტელეფონის შეცვლა ძველ შედეგს მალავს.
კურიერის ავტომატური პერიოდული შემოწმების job კვლავ მოგვიანებით ჩასართავია.

## თანხის დაბრუნება და უკუმიტანის ხარჯი

მომხმარებლისგან **მთელი შეკვეთის** მიღებისა და შემოწმების შემდეგ არსებული
„თანხის დაბრუნება“ ფანჯარა ითხოვს უკუმიტანის ხარჯს და გადამხდელს. ჯერ აჩვენებს
სერვერზე დათვლილ თანხას; შემდეგი ღილაკია „დადასტურება და 90.00 ₾-ის დაბრუნება“.
წინასწარი შემოწმება თანხას არ აბრუნებს. ხელმოწერილი, 15-წუთიანი დადასტურება
უკავშირდება შეკვეთასა და ყველა პირობას; შეცვლილი ფორმა ახალ გადამოწმებას ითხოვს.

- გადახდილია 100, უკუმიტანა 10, იხდის მომხმარებელი: ბანკში მიდის 90;
  აუცილებელია მომხმარებლის თანხმობის მონიშვნა და მიზეზი.
- გადახდილია 100, უკუმიტანა 10, იხდის FlexDrive: ბანკში მიდის სრული 100;
  10 რჩება ცალკე დაფიქსირებულ ხარჯად.
- გაგზავნამდე გაუქმებისას რჩება სრული თანხის დაბრუნება, უკუმიტანის დაქვითვის გარეშე.

გამოიყენება იგივე BOG refund endpoint; ნაწილობრივის JSON შეიცავს `amount`-ს.
მიღებული `action_id` საბოლოო გადარიცხვას არ ნიშნავს. მხოლოდ დადასტურებული
callback/payment-details, რომელიც ემთხვევა მოთხოვნის მოქმედებას, ზუსტ თანხას,
საწყის გადახდას და ჯამურ დაბრუნებას, ასრულებს დაბრუნებას.
უცნობი პასუხისას იგივე UUIDv4/idempotency key და გაყინული თანხა გამოიყენება;
მიმდინარე მოთხოვნის პირობების შეცვლა აკრძალულია. ბანკის უარის შემდეგ შეიძლება
ახალი მოთხოვნა; ყველა მცდელობის ჩანაწერი ინახება. დაგვიანებული პასუხი უკვე
დადასტურებულ დაბრუნებას მოლოდინში ან უარყოფილში ვერ დააბრუნებს.

შეკვეთის თავდაპირველი `total` არ იცვლება. თანხა, გადამხდელი, თანხმობა, მიზეზი,
დაქვითვა და ხარჯი ინახება refund transaction-ის გაყინულ `refund_request.settlement`-ში.
90/100 დაბრუნებისას შეკვეთის გადახდის მდგომარეობაა `partially_refunded`;
90-ლარიანი refund მოვლენა კი დასრულებულია (`refunded`). მთელი საქონლის დაბრუნება
ასრულებს შეკვეთას და მიღებული მარაგი მეორედ აღარ ემატება.

ბუღალტრის HTML/Excel და ბიზნესის ფინანსები აჩვენებს **რეალურად დაბრუნებულ თანხას**,
უკუმიტანისთვის დაქვითულ თანხასა და უკუმიტანის ხარჯს ცალ-ცალკე. საქონლის გაყიდვა
და რაოდენობა სრულად უკუიქცევა, 10 ლარი პროდუქტის მოგებად არ ითვლება. ხარჯი
ოპერატორის მიერ დაფიქსირებული თანხაა და არ ადასტურებს კურიერის ინვოისის გადახდას.
ძველი დაბრუნების დაუფიქსირებელი უკუმიტანის ხარჯი უცნობად რჩება. SKU-ძიებაში
შეკვეთის საფასურები პროდუქტებს არ ნაწილდება. ანგარიშის „ყველა“ ხედში საქონელი
და ფულადი დაბრუნება უარყოფითია; შეკავებული საფასური დადებითად აისახება ერთხელ.
უკუმიტანის ხარჯი ცალკე პერიოდით ითვლება — ქვემოთ აღწერილი ბიზნესის ანგარიშგების
წესით. „დაბრუნებულებში“ ორივე ტიპის დასრულებული ფულადი დაბრუნება შედის.

პირადი კაბინეტის სია/დეტალი, შეკვეთის საჯარო შეჯამება და სტუმრის ნომრით/ტელეფონით
შემოწმება იღებს `refund_summary`-ს: მდგომარეობა, თანხა და შეთანხმებული დაქვითვა.
მოლოდინი/უარი არ ჩანს დასრულებულ თანხის დაბრუნებად; ბანკის ნედლი პასუხი,
შიდა მიზეზი და ოპერატორის მონაცემები მომხმარებელს არ გადაეცემა.

ამ ფანჯარაში ერთი საბოლოო ანგარიშსწორებაა მთელი საქონლის დაბრუნებაზე;
ცალკეული ნივთების/რაოდენობების ნაწილობრივი დაბრუნება, შემდგომი დამატებითი
კომპენსაცია და RedCap-ის ავტომატური უკუდაჯავშნა ამ ცვლილებაში არ შედის.
უცხო/შეუსაბამო ნაწილობრივი დაბრუნება და უკვე დასრულებულის შემდეგ ბანკში
გამოჩენილი დამატებითი დაბრუნება ხელით შეჯერებისთვის ინიშნება.

ჩართვას სჭირდება backend + frontend დეპლოიმენტი და `0039_order_partial_refund_status`
მიგრაცია (`python manage.py migrate`). მიგრაცია მხოლოდ არჩევანის მდგომარეობას ამატებს;
არსებული შეკვეთების თანხებს არ გადაწერს. ბიზნესბაზებზე აქ არ გაშვებულა. რეალური
ბანკის დაბრუნება და პრინტერის/RedCap-ის ოპერაცია ცალკე კონტროლირებად შემოწმებას საჭიროებს.

## ბიზნეს პანელი, ბუღალტერია და Excel

ფინანსებში თბილისი/რეგიონი ერთ RedCap ნაწილშია. ძველი შიდა თბილისის ბლოკი
ამოღებულია. ნულოვანი ბუფერის მთავარი ბლოკი დამალულია; მომავალში შეკვეთაზე
დაფიქსირებული ბუფერი გამოჩნდება ცალკე, საკურიერო ფასთა სხვაობასთან შერევის გარეშე.

`commerce/courier_reporting.py` არის ბიზნესისა და ბუღალტერიის საერთო წყარო.
შეკვეთაზე შენახული ტარიფი, მომხმარებელზე დარიცხული მიტანა, ბუფერი და RedCap-ის
გზავნილის პასუხის `booked_price` სხვადასხვა სვეტებია. საბანკო თანხა სხვაობისას
არ იცვლება. შექმნილი გზავნილების ჯამი იყენებს **შექმნის თარიღს**, არა გადახდისას
დათვლილ ფასს. გაუგზავნელი/გაურკვეველი მოთხოვნა დაჯავშნილ ფასად არ ითვლება.
უცნობი ფასი სრულ ჯამს უცნობს ტოვებს; სხვაობა და გაუქმებული გზავნილის შესაძლო
საფასური ცალკე გადასამოწმებელია. გაუქმებული გზავნილები ფასების ჯამში არ შედის.
ეს ჯამი არც პროვაიდერის ინვოისის დავალიანებაა და არც გადახდილი ხარჯის მტკიცებულება.
Private API-ის ისტორიული `courier_payable` გასაღები ამ შექმნილი ფასების ჯამს ატარებს.

`commerce/return_costs.py` ადგენს უკუმიტანის ხარჯს **ერთი დაბრუნებისთვის ერთხელ**:
პირველი გაგზავნილი refund მოთხოვნის გაყინული settlement და მისი შექმნის დრო.
ბანკის უარი/timeout ჩანაწერს არ შლის. განმეორებითი მოთხოვნა იგივე ხარჯს ინარჩუნებს
და მას ახალ თვეში არ გადააქვს. სხვა ხარჯით განმეორება უარყოფილია; შემდგომი
ხარჯის შესწორება ამ ფანჯრიდან არ სრულდება. ჯერ დაუფიქსირებელი ან არასწორი ხარჯი
უცნობად რჩება. მომხმარებლისგან დაქვითვა ფულად აღირიცხება მხოლოდ საბოლოოდ
დადასტურებულ refund-ზე. შესაბამისად სექტემბრის ხარჯი10 და ოქტომბრის refund90
სხვადასხვა პერიოდებშია — სექტემბერში ხარჯი10, ოქტომბერში დაბრუნება90/დაქვითვა10.

ანგარიშის გახსნა მხოლოდ ბაზის SELECT-ებს აკეთებს. „ოპერაციებში“ არის RedCap-ის
გზავნილების ფილტრი/გვერდები, თრექინგი, ბოლო შემოწმება, უსაფრთხო გაფრთხილებები
და დაბრუნების თანხები. გაურკვეველი შექმნა ცალკე მდგომარეობაა; გაგზავნად არ ინიღბება.
ბანკის `error_code`-ით შესაჯერებელი დასრულებული refund-იც საყურადღებო სიაში ხვდება.
პროვაიდერის ნედლი შეცდომა, საიდუმლო/მისამართი/ტელეფონი ანგარიშში არ გადადის.
სინქრონიზაციის ბოლო **შენახული ანგარიში** არ არის cron-ის აქტიურობის მტკიცებულება;
ამ გვერდის განახლება არც RedCap-ს იძახებს და არც პერიოდულ სამუშაოს რთავს.

ბუღალტერიის შეკვეთის/Excel-ის მთავარ ცხრილში ტარიფი ფულადი გაყიდვის/დაბრუნების
თანხაა, ხოლო RedCap-ის ფასი/სხვაობა და უკუმიტანის ხარჯი საინფორმაციო სვეტებია;
მათი კოპიები ყოველ გადახდაზე არ ჯამდება. ცალკე საერთო ფუნქციებით დათვლილი
შექმნილი გზავნილებისა და უკუმიტანის ხარჯის პერიოდული ჯამები ბიზნესს ემთხვევა.
Excel-ს ემატება „უკუმიტანის ხარჯი“ და, შესაბამისი გზავნილების არსებობისას,
„RedCap გზავნილები“ ფურცლები. SKU-ძიებისას შეკვეთის საფასურების ფურცლები არ
ნაწილდება პროდუქტზე და არ ახლავს ექსპორტს. ძველი EasyWay/internal თანხების
გაყინული შეკვეთის სურათი წაკითხვადია; ახალი RedCap გზავნილების ანგარიშში არ ერევა.

დამატებითი schema migration ამ პანელის ცვლილებას არ სჭირდება; წინა თანხის
დაბრუნების `0039` კვლავ გასაშვებია deployment-ზე. ამ სამუშაოში ბიზნესბაზა, ბანკი,
RedCap, გარემოს ცვლადები და პერიოდული სამუშაოს კონფიგურაცია არ შეცვლილა.

## Checkout და მისამართი

API-ის `/locations` არის ხუთი **საკურიერო ზონა**, არა ყველა ქალაქის ცნობარი:
თბილისი, შემოგარენი, რეგიონის ქალაქები, სოფლები და მაღალმთიანი დასახლებები.
Checkout-ში არის მიმართულების ერთი არჩევანი და რეალური ქალაქის/სოფლის ცალკე ველი.
ბანკის snapshot და შეკვეთა „ბათუმს“ ზოგადი ზონის სახელით არ ცვლის.
RedCap-ის `receiver_city` იღებს ზონის ზუსტ სახელს, სრული მისამართი — რეალურ დასახლებას.
შემოგარენის/მაღალმთიანი დასახლების სწორი ზონა ოპერატორმა გაგზავნამდე გადაამოწმოს.

თავსებადობისთვის დარჩენილი `delivery_region_id` და `delivery_city_id` ორივე
არჩეული RedCap ზონის ID-ს ატარებს; UI-ში ორი განმეორებული არჩევანი აღარ ჩანს.
ფასის ხელმოწერა აკავშირებს კალათას, რაოდენობას, წონას, ზონას და ტარიფის ვერსიას.
ცვლილება ან ვადის გასვლა ხელახალ დათვლას ითხოვს. გადახდის დაწყების შემდეგ ფასი
ფიქსირდება; ბანკის მოგვიანებით მიღებული პასუხი მას ახალ ტარიფზე არ ცვლის.
ძველი გაყინული ბანკის snapshot იკითხება; ახალი EasyWay ფასი აღარ იქმნება.

თბილისის სერვისია `same_day`, შემოგარენის — `Dgesshemog`; შუადღის შემდეგ
`next_day`-ზე გადართვა არ ხდება: API-მ 17:21-ზე `same_day`-სთვის „ხვალ“,
`next_day`-სთვის „ზეგ“ დააბრუნა. რეგიონებშია `RegionCity`, `sofeli`, `Magalmtiani`.
თბილისის ტექსტი ვადას შეკვეთის დამუშავებას უკავშირებს; რეგიონში 3–4 დღე სავარაუდოა,
მაღალმთიანში მიმართულებით ზუსტდება. პროვაიდერის გვერდზე იყო 2–5 სამუშაო დღე
და მაღალმთიანში 2–7; კონკრეტული ვალდებულება ხელშეკრულებას უნდა შეესაბამებოდეს.

## გარემოში ჩართვა — დარჩენილი ნაბიჯები

1. backend და დაწყვილებული frontend გამოქვეყნდეს შეთანხმებულად;
   ძველი frontend ახალი ზონების ფორმას სწორად ვერ განმარტავს.
2. backend runtime-ში შეივსოს `REDCAP_API_KEY`, `REDCAP_SENDER_NAME`,
   `REDCAP_SENDER_PHONE`, `REDCAP_SENDER_CITY`, `REDCAP_SENDER_ADDRESS`.
   ქალაქი ზონის ზუსტი სახელია; აღების ქუჩა/ნომერი მისამართში იწერება.
   მაგალითია `.env.staging.example`; მოქმედი `.env` არ შეცვლილა.
3. ქვითრის იურიდიული მონაცემები პირდაპირ შეივსოს `ORDER_RECEIPT_SELLER_*`-ში;
   EasyWay პარამეტრებზე fallback აღარ არის. ბანკის/supplier-ის პარამეტრები არ იცვლება.
4. ჩვეულებრივი სარეზერვო ასლის შემდეგ `python manage.py migrate` დაამატებს
   `commerce.0037` და `0038`-ს; მონაცემების წაშლის მიგრაცია არ არის.
5. ადმინიდან ერთხელ ჩამოიტვირთოს ტარიფები ან გაეშვას
   `python manage.py refresh_redcap_references`; ცნობარის გარეშე ფასი არ გაიცემა.
6. DigitalOcean-ში გამოირთოს EasyWay-ის სამუშაო. სტატუსებისთვის შესაბამის
   არსებულ worker/job გარემოში გამოყენებულ იქნას
   `python manage.py sync_redcap_tracking --limit 100 --min-age-minutes 10`.
   დასაწყისში შეიძლება `--dry-run`; გრაფიკი, მაგალითად ყოველ 10 წუთში.
   **ტარიფების cron არ არის საჭირო.** ახალი ფასიანი რესურსი არ შექმნილა;
   სტატუსების სამუშაოს გაშვების ხარჯი არსებული DigitalOcean კონფიგურაციით განისაზღვრება.
7. შესაბამის თანამშრომლებს მიენიჭოს შეკვეთის შეცვლისა და ტარიფის განახლების უფლებები.
8. შეთანხმებულ კონტროლირებულ გარემოში შემოწმდეს ორივე Checkout, ბანკის სრული
   ციკლი, ერთი რეალური საცდელი დაჯავშნა, თითო ყუთის PDF/ბეჭდვა, სტატუსები და
   პროვაიდერისგან დაშვებული გაუქმება. რეალური დაჯავშნის დრო ცალკე შეთანხმდეს.
9. მფლობელმა გარემოდან მოხსნას EasyWay გასაღებები და პროვაიდერთან გააუქმოს.

EasyWay DB ველები/ცხრილები და მიგრაციების ისტორია პასიურად დარჩა upgrade-ისა
და ისტორიული წაკითხვისთვის. მათზე მოქმედი საკურიერო API/ადმინის მოქმედება აღარ არის.

## შემოწმების გამეორება და ფარგლები

ბუღალტერიის/ტარიფების UI, მომხმარებლის სტატუსისა და გაუქმების/refund დაცვის 282 backend ტესტი წარმატებულია;
migration drift, შეცვლილი Python ფაილების სინტაქსი და whitespace შემოწმებებიც გადის.
სტუმრის სტატუსის დახვეწისთვის დაემატა 6 რეალურ Vue კომპონენტზე გაშვებული ტესტი;
Checkout-ის 5 ტესტთან ერთად 11 frontend ტესტი გადის. frontend typecheck და scoped ESLint წარმატებულია.

```powershell
.\venv\Scripts\python.exe _qa/run_redcap_tests.py
.\venv\Scripts\python.exe _qa/run_redcap_tests.py --check-migrations
```

Harness იყენებს ერთჯერად in-memory SQLite-ს და ბლოკავს გამავალ ქსელს.
მოიცავს RedCap კლიენტს/ცნობარს, ორივე Checkout-ს, უფლებებს/CSRF/PDF-ს,
დუბლირებას/timeout-ს/აღდგენას, ჯგუფურ სტატუსებს/lease-ს, გაყინულ ბანკის პასუხებს,
refund/reconciliation-ს, ბუღალტერიას და ბიზნეს პანელს. ბიზნესბაზას არ ეხება.

Frontend: `npm run typecheck`, შეცვლილი ფაილების ESLint და
`node --test tests/checkoutDraft.test.mjs tests/redcapCheckout.test.mjs`.
მოწმდება ნამდვილი Vue composable და Checkout-ის SSR კომპონენტი.
სერვერი ან ბრაუზერი არ გაშვებულა; რეალური viewport/პრინტერი/საკურიერო ციკლი
ამ შედეგებით არ იგულისხმება.

მთელი ისტორიული suite-ის წარმატება არ არის განცხადებული: ძველი
`test_card_payment_flow` პირველ გაშვებაში ეცემოდა გაუნახლებელი `internal_sku`
fixture-ით (`catalog_published_requires_sku`). მიმდინარე ფასის/ბანკის ინტეგრაცია
მოწმდება განახლებული `test_bog_callback_flow`-ით. ამოღებული EasyWay-ის სერვისების
ტესტები RedCap-ის ტესტებმა ჩაანაცვლა. CKEditor/staticfiles გაფრთხილებები წინარეა.
