## შესრულებული ეტაპები

1. ავტორიზებული დოკუმენტაციისა და რეალური ცნობარების read-only შემოწმება.
2. backend API კლიენტი: უსაფრთხო შეცდომები, ავტორიზაცია, შეზღუდული PDF,
   საიდუმლოების გადატანის გარეშე redirect და ავტომატური mutation retry გამორთულია.
3. ტარიფების/ზონების/სტატუსების ატომური შენახვა და ადმინიდან ხელით განახლება.
4. ორივე Checkout-ის ადგილობრივი, ხელმოწერილი ფასი; ბანკისთვის ფასის გაყინვა.
5. დამოუკიდებელი გზავნილის ჩანაწერი, ადმინის შექმნა და გაურკვეველი შედეგის აღდგენა.
6. ოფიციალური PDF სტიკერი და პროვაიდერის წესით დაშვებული გაუქმება.
7. სტატუსების ჯგუფური შემოწმება, lease დაცვა, ადმინის ისტორია და სამუშაო ბრძანება.
8. RedCap-ის აღრიცხვა ბუღალტერიასა და ბიზნეს პანელში; ქვითრის პარამეტრების
   EasyWay-ის გამგზავნის პარამეტრებიდან გამოყოფა.
9. დაწყვილებული frontend-ის კალათისა და Buy Now Checkout, მისამართი და ტექსტები.
10. მოქმედი EasyWay კლიენტის/გაგზავნის/ცნობარების/სტატუსების მოდულებისა და
    ადმინის ღილაკების ამოღება. ძველი ბრძანებები მოთხოვნის გარეშე ჩერდება.

## ადმინი და ოპერატორის მოქმედებები

**Commerce → RedCap ტარიფები:** შენახული ცხრილი, ზონები, საფასო კატეგორია და
ბოლო წარმატებული განახლება. „ტარიფების განახლება“ დადასტურებული POST-ით ცვლის
ცნობარს; არასრული პასუხი ძველ სწორ ცხრილს ინარჩუნებს. უჯრები ხელით არ რედაქტირდება.

**შეკვეთა → RedCap მიწოდება:** გზავნილის მდგომარეობა, თრექინგი, ყუთების რაოდენობა,
პროვაიდერის დაბრუნებული ფასი, კურიერის სტატუსი, შემოწმების დრო, შეცდომები და ბოლო
20 დაკვირვება. დაკვირვების დრო არის ჩვენი შემოწმების დრო, არა საკურიერო მოვლენის დრო.

1. ოპერატორი ამოწმებს გადახდილ შეკვეთას, მიმღებს, მისამართსა და ნივთებს.
2. შეფუთვის შემდეგ აჭერს „RedCap-ში გზავნილის შექმნა“.
3. უთითებს ყუთების რაოდენობას, მონიშნავს მზადყოფნას და ადასტურებს.
4. წარმატების შემდეგ ხსნის „სტიკერის გახსნა / ბეჭდვა — A4“.
5. PDF ფანჯრიდან ბეჭდავს; თითო ყუთს აკრავს შესაბამის გვერდს და გადასცემს კურიერს.
6. პროგრესი ახლდება ხელით ან სტატუსების პერიოდული სამუშაოთი.

შექმნა ფიზიკურ გადაცემად არ აღირიცხება; „გზაშია“ დგება შესაბამისი სტატუსის მიღებისას.
გაურკვეველი პასუხის შემდეგ „შექმნა“ იბლოკება. „გაგზავნის შედეგის გადამოწმება“
ეძებს არსებულ გზავნილს ჩვენი შეკვეთის ნომრით და მხოლოდ ზუსტ დამთხვევას აკავშირებს.
თუ დამთხვევა ვერ დასტურდება, ოპერატორი ამოწმებს RedCap-ის პანელში;
ახალი მოთხოვნა ავტომატურად არ იგზავნება. პროვაიდერის დუბლირებული თრექინგის
პასუხიც განმეორებით დაჯავშნას არ ხდის დასაშვებს.

გაუქმებამდე მოწმდება მიმდინარე სტატუსის `can_cancel`. გზავნილის გაუქმება
**არ აუქმებს FlexDrive შეკვეთას, არ აბრუნებს თანხას და არ ცვლის მარაგს**.
გაურკვეველი გაუქმება სტატუსის კითხვით მოწმდება. გაუქმებული გზავნილის ხელახლა
დაჯავშნის ავტომატური ფუნქცია ამ ეტაპზე არ არის.

**RedCap სინქრონიზაციის ანგარიშები:** ცვლილებები და პრობლემები. უცვლელი წარმატებული
შემოწმება ახალ ანგარიშს არ ქმნის; ბიზნეს პანელი ბოლო შენახულ ანგარიშს აჩვენებს,
ხოლო თითო გზავნილს საკუთარი შემოწმების დრო აქვს. სტატუსები არ იწყებს refund-ს,
მარაგის აღდგენას და არ ხსნის გაუქმებულ/დაბრუნების პროცესში მყოფ შეკვეთას.

## სტიკერი

მფლობელის A4 ფოტოზე ჩანს ლოგო, QR, კომპანია, იდენტიფიკატორები/შეკვეთის ნომერი,
თარიღები, ყუთის ინდექსი, წონა, პროდუქტები/რაოდენობები და მიმღების საკონტაქტო
მონაცემები/მისამართი. ფოტოს პირადი მონაცემები პროექტში არ შენახულა.

ვიყენებთ **RedCap-ის ოფიციალურ PDF-ს**, საკუთარი QR-ისა და მაკეტის გარეშე:
`GET /orders/{tracking}/label?size=a4|a5|zebra`. დოკუმენტაციით თითო ამანათს თავისი
QR და გვერდი აქვს; `zebra` არის 100×50 მმ. ადმინში არის A4, A5, თერმული ფორმატი
და ჩამოტვირთვა. რეალური PDF/პრინტერი პირველი საცდელი დაჯავშნის შემდეგ მოწმდება.
PDF მხოლოდ უფლებამოსილ backend ადმინს გადაეცემა private/no-store პასუხით;
გასაღები და ავტორიზებული პროვაიდერის მისამართი frontend-ში არ ხვდება.

## Checkout და მისამართი

API-ის `/locations` არის ხუთი **საკურიერო ზონა**, არა ყველა ქალაქის ცნობარი:
თბილისი, შემოგარენი, რეგიონის ქალაქები, სოფლები და მაღალმთიანი დასახლებები.
Checkout-ში არის მიმართულების ერთი არჩევანი და რეალური ქალაქის/სოფლის ცალკე ველი.
ბანკის snapshot და შეკვეთა „ბათუმს“ ზოგადი ზონის სახელით არ ცვლის.
RedCap-ის `receiver_city` იღებს ზონის ზუსტ სახელს, სრული მისამართი — რეალურ დასახლებას.
შემოგარენის/მაღალმთიანი დასახლების სწორი ზონა ოპერატორმა გაგზავნამდე გადაამოწმოს.

თავსებადობისთვის დარჩენილი `delivery_region_id` და `delivery_city_id` ორივე
არჩეული RedCap ზონის ID-ს ატარებს; UI-ში ორი განმეორებული არჩევანი აღარ ჩანს.
ფასის ხელმოწერა აკავშირებს კალათას, რაოდენობას, წონას, ზონას და ტარიფის ვერსიას.
ცვლილება ან ვადის გასვლა ხელახალ დათვლას ითხოვს. გადახდის დაწყების შემდეგ ფასი
ფიქსირდება; ბანკის მოგვიანებით მიღებული პასუხი მას ახალ ტარიფზე არ ცვლის.
ძველი გაყინული ბანკის snapshot იკითხება; ახალი EasyWay ფასი აღარ იქმნება.

თბილისის სერვისია `same_day`, შემოგარენის — `Dgesshemog`; შუადღის შემდეგ
`next_day`-ზე გადართვა არ ხდება: API-მ 17:21-ზე `same_day`-სთვის „ხვალ“,
`next_day`-სთვის „ზეგ“ დააბრუნა. რეგიონებშია `RegionCity`, `sofeli`, `Magalmtiani`.
თბილისის ტექსტი ვადას შეკვეთის დამუშავებას უკავშირებს; რეგიონში 3–4 დღე სავარაუდოა,
მაღალმთიანში მიმართულებით ზუსტდება. პროვაიდერის გვერდზე იყო 2–5 სამუშაო დღე
და მაღალმთიანში 2–7; კონკრეტული ვალდებულება ხელშეკრულებას უნდა შეესაბამებოდეს.

## გარემოში ჩართვა — დარჩენილი ნაბიჯები

1. backend და დაწყვილებული frontend გამოქვეყნდეს შეთანხმებულად;
   ძველი frontend ახალი ზონების ფორმას სწორად ვერ განმარტავს.
2. backend runtime-ში შეივსოს `REDCAP_API_KEY`, `REDCAP_SENDER_NAME`,
   `REDCAP_SENDER_PHONE`, `REDCAP_SENDER_CITY`, `REDCAP_SENDER_ADDRESS`.
   ქალაქი ზონის ზუსტი სახელია; აღების ქუჩა/ნომერი მისამართში იწერება.
   მაგალითია `.env.staging.example`; მოქმედი `.env` არ შეცვლილა.
3. ქვითრის იურიდიული მონაცემები პირდაპირ შეივსოს `ORDER_RECEIPT_SELLER_*`-ში;
   EasyWay პარამეტრებზე fallback აღარ არის. ბანკის/supplier-ის პარამეტრები არ იცვლება.
4. ჩვეულებრივი სარეზერვო ასლის შემდეგ `python manage.py migrate` დაამატებს
   `commerce.0037` და `0038`-ს; მონაცემების წაშლის მიგრაცია არ არის.
5. ადმინიდან ერთხელ ჩამოიტვირთოს ტარიფები ან გაეშვას
   `python manage.py refresh_redcap_references`; ცნობარის გარეშე ფასი არ გაიცემა.
6. DigitalOcean-ში გამოირთოს EasyWay-ის სამუშაო. სტატუსებისთვის შესაბამის
   არსებულ worker/job გარემოში გამოყენებულ იქნას
   `python manage.py sync_redcap_tracking --limit 100 --min-age-minutes 10`.
   დასაწყისში შეიძლება `--dry-run`; გრაფიკი, მაგალითად ყოველ 10 წუთში.
   **ტარიფების cron არ არის საჭირო.** ახალი ფასიანი რესურსი არ შექმნილა;
   სტატუსების სამუშაოს გაშვების ხარჯი არსებული DigitalOcean კონფიგურაციით განისაზღვრება.
7. შესაბამის თანამშრომლებს მიენიჭოს შეკვეთის შეცვლისა და ტარიფის განახლების უფლებები.
8. შეთანხმებულ კონტროლირებულ გარემოში შემოწმდეს ორივე Checkout, ბანკის სრული
   ციკლი, ერთი რეალური საცდელი დაჯავშნა, თითო ყუთის PDF/ბეჭდვა, სტატუსები და
   პროვაიდერისგან დაშვებული გაუქმება. რეალური დაჯავშნის დრო ცალკე შეთანხმდეს.
9. მფლობელმა გარემოდან მოხსნას EasyWay გასაღებები და პროვაიდერთან გააუქმოს.

EasyWay DB ველები/ცხრილები და მიგრაციების ისტორია პასიურად დარჩა upgrade-ისა
და ისტორიული წაკითხვისთვის. მათზე მოქმედი საკურიერო API/ადმინის მოქმედება აღარ არის.
