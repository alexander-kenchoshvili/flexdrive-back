## როგორ მუშაობს

Wingo-ს მხარეს სტატუსის შეტყობინებები უკვე მხარდაჭერილია. შეკვეთის POST /orders-ში
ჩვენ ვამატებთ callback_url-ს: ჩვენი ბექენდის HTTPS მისამართს, ამ შეკვეთის public_token-ს
და ცალკე, სერვერის საიდუმლო გასაღებით ხელმოწერილ token-ს. Wingo-ს პროფილის ხელით
შეცვლა ახალი გზავნილებისთვის საჭირო აღარ არის; კონკრეტული შეკვეთის მისამართი უპირატესია.

Wingo აგზავნის order.created / order.status_changed შეტყობინებას. ჩვენი მიმღები ამოწმებს
კერძო მისამართის token-სა და შეკვეთის/გზავნილის შესაბამისობას. შემდეგ არსებული API გასაღებით
კითხულობს GET /orders/{internal-id}-ს და მხოლოდ მის დადასტურებულ მიმდინარე მონაცემს იყენებს.
შეტყობინებაში მითითებული სტატუსი, timestamp ან User-Agent ცვლილებას თვითონ ვერ ადასტურებს.
ერთი მერჩანტის/შეკვეთის მონაცემები სხვას ვერ მიებმება.

საჭირო არ არის ახალი კრონი, მუდმივი polling, background thread ან ცალკე worker-სერვისი.
ეს ავტომატიზაცია განკუთვნილია უკვე არსებულ საჯარო ბექენდზე გასაშვებად; Wingo პირდაპირ
localhost-ს ვერ დაუკავშირდება. ლოკალურად შესაძლებელია მიმღების ტესტი და ხელით API შემოწმება.

## ამოქმედების პარამეტრი

ბექენდის runtime-ში დაემატა:

| ცვლადი | მნიშვნელობა |
|---|---|
| WINGO_WEBHOOK_PUBLIC_URL | https://ბექენდის-ჰოსტი/api/commerce/wingo/webhook/ |
| WINGO_WEBHOOK_SECRET | ცარიელი, თუ Wingo-სთან ცალკე HMAC საიდუმლო შეთანხმებული არ არის |

PUBLIC_URL არის ფიქსირებული HTTPS ძირი, token-ების გარეშე; მათ თითოეულ გზავნილს კოდი
თავად უმატებს. URL-ში query, fragment, მომხმარებელი/პაროლი ან სხვა endpoint დაუშვებელია.
კერძო სრული callback_url მომხმარებლის API-ში ან ადმინის HTML-ში არ გამოჩნდება.
უკვე შექმნილი ძველი გზავნილის callback არ იცვლება ამ ეტაპზე: მას ხელით გადამოწმება აქვს.

production რეჟიმში PUBLIC_URL-ის არქონა ახალი booking-ის გაგზავნამდე მკაფიო შეცდომას იძლევა.
test რეჟიმში ცარიელი მისამართი დასაშვებია და ადმინი აჩვენებს, რომ ამ გზავნილზე ავტომატური
განახლების მისამართი არ გაგზავნილა. ლოკალურ .env-ში საჯარო მისამართი არ მოგვიგონია.
თუ Wingo-სთან HMAC შეთანხმდება, SECRET-ის შევსება დამატებით მოითხოვს raw JSON-ზე
