## დასკვნა

ინტეგრაციის ძირითადი შესაძლებლობები დოკუმენტირებულია: შეკვეთის შექმნა,
PDF, ცნობარები, ტარიფები, ფასის/თარიღის შეფასება და სტატუსის შეტყობინებები.
სრულ ციკლს ჯერ აკლია გაუქმების/რედაქტირების კონტრაქტი, უკუგზავნილის ნაკადი,
რამდენიმე შეფუთვის წესი და timeout-ის შემდეგ უსაფრთხო აღდგენის დეტალები.
სახელისა და გასაღების შეცვლა საკმარისი არ იქნება. ბანკის დაბრუნების ძირითადი
მექანიზმი და უკვე გამიჯნული ფინანსური თანხები ხელახლა ასაწყობი არ არის.

## წვდომები და გარემო

- API key გამოიყენება backend-იდან Bearer ან X-API-Key სათაურით.
- user/password, სავარაუდოდ, Wingo Dashboard-ის შესასვლელია. API-ისთვის
  პაროლით login-ის გზა ფაილში აღწერილი არ არის; ამ დანიშნულებას დასტური სჭირდება.
- მოთხოვნის userId არის მერჩანტის შიდა ID; username/email-თან მისი იგივეობა
  არ უნდა ვივარაუდოთ. POST /orders-ში სავალდებულოა. ფასის შეფასებისას key-დან
  ავტომატურად განსაზღვრა ცალკე დოკუმენტირებულია.
- ფაილის მთავარი base URL production-ადაა მონიშნული; ცნობარების მაგალითებში
  apiwingo.vercel.app-იც არის. არცერთი მისამართი თავისთავად არ ადასტურებს sandbox-ს.
  საჭიროა გამოგზავნილ test account/key-ს შესაბამისი ზუსტი API და Dashboard URL,
  userId და დადასტურება, რომ საცდელი გზავნილი რეალურ კურიერს/ინვოისს არ ქმნის.
- გასაღები, პაროლი და webhook-ის შესაძლო ცალკე საიდუმლო front/repo-ში არ შევა.

## ფასები და მიტანის ვადა

1. შეინარჩუნება მომხმარებლისთვის ერთი შეთანხმებული მომსახურება; არჩევანი
   „სწრაფი/სტანდარტული“ ამ ეტაპზე მოთხოვნილი არ არის. Wingo-ს ტიპი1/ტიპი2-ის
   არჩევას მისი რეალური დაფარვა, ფასი და ვადა განსაზღვრავს.
2. GET /merchant-tariffs და /regional-tariffs ეფექტურ ფასებს აღწერს. პასუხის
   სრული სქემა არ არის მოცემული. ჯერ უნდა შევადაროთ იმავე ანგარიშის
   estimate-service-fee-სა და სატესტო შექმნის რეალურ თანხას.
3. თუ ცხრილი საკმარისია, ფასები ჩვენთან შეინახება და checkout არ გამოიძახებს
   Wingo-ს ყოველი მისამართის არჩევაზე. თუ ფასი დამატებით უცნობ პირობებზეა
   დამოკიდებული, ადგილობრივი ფორმულა წინასწარ არ უნდა გამოვიგონოთ.
4. serviceFee-ის ხელით გაგზავნა დოკუმენტირებულია, მაგრამ ამას უცვლელი ფასის
   ან თვითნებური ტარიფის არჩევის გარანტიად არ მივიჩნევთ. შეთანხმების გარეშე
   გადახდილი თანხის Wingo-ზე იძულებით გადატანა არ უნდა მოხდეს.
5. COD გამორთული იქნება: recipientPaymentDue=0. ეს არ ადასტურებს, რომ კურიერის
   მომსახურების საფასურიც მიმღებს არ დაეკისრება — ინვოისის/მერჩანტის პირობა ცალკე დასტურდება.
6. isB2b არ უდრის ავტომატურად ჩვენს buyer_type=legal_entity-ს. ფაილში ის Wingo-ს
   ცალკე B2B ტარიფს რთავს; მისი დანიშნულება ჩვენს ხელშეკრულებას უნდა შეესაბამებოდეს.
7. Wingo-ს estimate-delivery-date ითვალისწინებს ლოკაციას, მომსახურების ტიპს,
   შესაძლო აღების რეგიონს და UTC+4 cutoff13:00-ს. API-ით შეკვეთის შექმნა მაინც
   ოპერატორის მიერ ნივთების მომზადების შემდეგ მოხდება. შეძენის დრო თავისთავად
   ვერ წარმოადგენს პროვაიდერთან მოთხოვნის გაგზავნის დროს.
8. public schedule მიუთითებს რეგიონულ კონკრეტულ კვირის დღეებზე. იმავე/მეორე
   დღის თბილისის დაპირება და რეგიონული ვადები Wingo-სთან თავიდან შესამოწმებელია.

## პროვაიდერისგან დასაზუსტებელი პუნქტები

1. ზუსტი სატესტო API/Dashboard URL და userId; საბოლოო production წვდომების სხვაობა.
2. PUT /orders-ის სრული კონტრაქტი: კონკრეტული შეკვეთის მითითება, დასაშვები ველები,
   გაუქმების გზა/ეტაპები, შედეგის გადამოწმება და შესაძლო საკურიერო გადასახადი.
3. მომხმარებლისგან უკვე ჩაბარებული ნივთის უკუგზავნილი: API თუ პანელი, ახალი ნომერი,
   pickup/receiver რეგიონის ფასი, მერჩანტზე დარიცხვა და მომხმარებელთან სტიკერის დაკვრა.
4. რამდენიმე ყუთი: ერთ გზავნილად თუ ცალკე order-ებად; წონა როგორ ჯამდება; label-ის
   PDF თითო ყუთს აძლევს თუ არა ინდივიდუალურ მარკირებას. products.quantity არ არის
   შეფუთვების რაოდენობის დოკუმენტირებული ველი. საჭიროა სატესტო PDF ნიმუშიც.
5. ტარიფების სრული JSON სქემა, დღგ, დიდი/მოცულობითი ავტონაწილების დათვლის/მიღების
   წესი, ფასის საბოლოო დადასტურება, serviceFee-ის override და B2B-ის დანიშნულება.

   ზუსტი სტრუქტურა; /localities რატომ ითხოვს Dashboard cookie-ს. username/password
   სერვერული scraping-ის ან მუდმივი სესიის საჭიროებად არ უნდა ვივარაუდოთ.
7. supplierOrderId-ის უნიკალურობა/idempotency: timeout-ის შემდეგ GET /orders-ში
