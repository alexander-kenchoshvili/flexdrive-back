# Wingo-ს პანელიდან გაუქმება და უკუგზავნილი

მომხმარებლის გადაწყვეტილებით, გაუქმებასა და უკუგზავნილს ოპერატორი Wingo-ს
პანელში აფორმებს. ჩვენი სისტემა ამ მოქმედებებისთვის დაუდასტურებელ API-ს არ იყენებს.

## გაუქმება გაგზავნამდე

1. Wingo-ს პანელში მოძებნეთ თავდაპირველი გზავნილი და გააუქმეთ, სანამ ამის უფლება გაქვთ.
2. ჩვენს შეკვეთაზე გამოიყენეთ **Wingo-ს სტატუსის განახლება**. Webhook-იც იმავე
   ავთენტიფიცირებული GET-ით ამოწმებს მდგომარეობას.
3. მხოლოდ ზუსტად შესაბამისი გზავნილის მიღებული სტატუსი `10` აფიქსირებს გაუქმების
   გადამოწმების დროს. `4` (აღების გაუქმება) საკმარისი არ არის. ძველი/წინააღმდეგობრივი
   პასუხი, უცნობი გაგზავნის შედეგი, მიმდინარე შემოწმება, წარუმატებელი GET ან
   გადაუმოწმებელი ახალი webhook თანხის დაბრუნების უფლებას არ ხსნის.
4. **თანხის დაბრუნება** ცალკე მოქმედებაა. კვლავ სავალდებულოა ნივთების მდგომარეობა
   და დადასტურება, რომ მომხმარებელთან არ გაგზავნილა. სრული თანხა, მიტანის ჩათვლით,
   ბანკის იგივე დაცული, განმეორებითი ჩამოჭრისგან/დაბრუნებისგან დაცული ციკლით ბრუნდება.

თუ ნივთები უკვე აღებულია/ჩაბარებულია, სტატუსი `10` პირდაპირ refund-ს ვერ გახსნის.
საჭიროა უკან წამოღების შეთანხმება და ყველა ნივთის მიღება/შემოწმება.
შეკვეთა და გადახდა მარტო საკურიერო სტატუსით არ უქმდება; მარაგიც არ იცვლება.
გაუქმებული გზავნილი ახალი POST-ისთვის ხელახლა არ იხსნება.

## უკუგზავნილი და თანხა

1. Wingo-ს პანელში გააფორმეთ უკუგზავნილი.
2. ჩვენს გაგზავნილ/ჩაბარებულ შეკვეთაზე **დაბრუნების დაწყება** მოითხოვს ახალი
   უკუგზავნილის ნომერს და პანელში გაფორმების დადასტურებას.
3. ნომერი ინახება დაბრუნების ჩანაწერზე, ჩანს შეკვეთასა და დაბრუნების ადმინში,
   იძებნება დაბრუნებების სიაში. დაწყების ოპერატორი/დრო და ადმინის ისტორია ინახება.
   ნომერი იგივე მიტანის ნომერი ვერ იქნება; სხვა დაბრუნებაზე გამოყენებული ნომერიც
   უარყოფილია. განმეორებითი იგივე მოთხოვნა ახალ დაბრუნებას არ ქმნის.
4. **მიღება და შემოწმება** ადასტურებს ყველა ნივთის რაოდენობასა და მდგომარეობას.
   მხოლოდ ვარგისი რაოდენობა ემატება საკუთარ მარაგს, ერთხელ. ჯერ ბანკის მოქმედება არ სრულდება.
5. **თანხის დაბრუნება**: ჩაწერეთ რეალური უკუმიტანის ხარჯი (ან აშკარად `0`), აირჩიეთ
   გადამხდელი და ნახეთ თანხის წინასწარი დათვლა. Wingo-ს ახალი დაბრუნების ფორმაში
   უკუმიტანის ხარჯი ნაგულისხმევად შევსებული არ არის.
6. მხოლოდ ზუსტი ხელმოწერილი წინასწარი დათვლის შემდეგ დაადასტურეთ ბანკში დაბრუნება.

მაგალითი: ნივთი100 + მიტანა10 = გადახდილი110; უკუმიტანა10.
მომხმარებლის გადახდისას ბრუნდება90, კომპანიის გადახდისას110 და ცალკე აღირიცხება10 ხარჯი.
დაბრუნებული ფული, ორივე დაქვითვა და უკუმიტანის ხარჯი საერთო ბუღალტერიაში,
ბიზნესის ფინანსურ ანგარიშსა და XLSX-ში Wingo-სთვისაც სწორად ნაწილდება.
უკუმიტანის ხარჯის ერთადერთი ფინანსური წყარო კვლავ პირველი გაყინული refund-მოთხოვნაა;
ნომრის შენახვა მეორე ხარჯს არ ქმნის. ხარჯის პერიოდი და ბანკის დადასტურების პერიოდი ცალკეა.

## საზღვრები და გაშვება

- უკუგზავნილის ნომერი ოპერატორის ჩანაწერია; Wingo-ში მისი შექმნა, ეტიკეტი და
  მოძრაობის ნახვა მათ პანელში ხდება. უკუგზავნილის ავტომატურ ტრეკინგს არ ვაცხადებთ.
- კოდი არ ადასტურებს ცოცხლად, გამოჩნდება თუ არა კონკრეტული პანელის გაუქმება GET-ში.
  ამ ეტაპზე მხოლოდ სინთეზური, იზოლირებული კონტრაქტის ტესტებია; თუ GET სტატუსს10
  არ დააბრუნებს, ბლოკი დარჩება და საჭიროა Wingo-სთან გადამოწმება.
- ისტორიულ დაბრუნებებს ნომერი არ ევსებათ და არსებული თანხები/მოთხოვნები არ იცვლება.
  ძველი სტატუსი10 ახალი ავთენტიფიცირებული შემოწმების გარეშე გაუქმებას არ ადასტურებს.
- `commerce.0044_wingo_platform_returns`: ორი nullable ველი — დაბრუნების ნომერი
  და გზავნილის გაუქმების გადამოწმების დრო. რეალური ბანკის/კურიერის მოქმედება არ სრულდება.
- ფრონტს ცვლილება არ სჭირდება. backend-ის push/deploy მომხმარებლის მხარესაა;
  production0044 მხოლოდ ცალკე მოთხოვნის შემდეგ უნდა შესრულდეს.
- Wingo-ს სრული booked-price/გზავნილების ანგარიშგება და RedCap-ის წაშლა სხვა ეტაპია.
  აქ გასწორდა საერთო ფინანსური განაწილების მიერ Wingo-ს ცნობადობა.
